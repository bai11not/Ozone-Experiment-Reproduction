## 一、实验过程回顾

本次实验围绕 PE-DiffWaveNet 模型的四个核心维度——预测步长（pre_len）、历史窗口（seq_len）、扩散模块（use_diffusion）和随机种子（seed）——进行了系统性的对比与消融分析，共计完成 12 组有效实验（另有 1 组因代码 bug 作废并重命名归入主实验系列）。

实验流程为：先完成基准实验（seq_len=24, pre_len=6, diffusion=1, seed=42），再依次改变 pre_len、seq_len 进行参数扫描，然后完成所有扩散模块消融（seed=42），最后扩展到 seed=62 的 4 组主实验。每组实验生成标准化的四文件输出，最终汇总为统一对比报告。过程中还经历了一次 PE Graph 消融的代码 bug，将在下文详述。

## 二、技术挑战与解决

### 2.1 环境兼容性问题

实验中遇到的最棘手问题并非模型本身，而是运行环境的兼容性：

- **WSL (Linux) 下 Python 3.11 + numpy/scipy/geographiclib 的 C 扩展层频繁发生 segfault**，尤其是在 PE 密集计算（pe_window_step=1）时。经过反复排查（降级库版本、更换 geographiclib 版本等），最终确认是 WSL drvfs 与 Python C 扩展之间的平台级兼容问题。
- **解决方案**：切换到 Windows 原生 conda 环境 (torch_env)，并用纯 Python 实现替换 geographiclib（Haversine 公式）。

这让我深刻体会到：**在深度学习实验中，环境配置的稳定性往往比模型调参更耗时，也更重要**。生产级的实验流程应当优先确保基础环境的可靠。

### 2.2 PE 计算的内存稳定性

pe_window_step=1 意味着对每个站点的时间序列（7378 个点）进行逐时滑动窗口 PE 计算，95 个站点 × 6 个尺度 = 570 次调用。原始的 numpy 向量化实现在密集调用下出现了 Python 对象类型损坏（`'function' object is not iterable`、`'int' object is not subscriptable` 等不可思议的错误）。

**这类错误的排查是本次实验最大的收获之一**：
1. 看似"不可能"的 Python 错误（如字面量 `[0,0,0,0,0,0]` 变成 function）往往指向底层内存损坏；
2. 传统思路（清除 pycache、重装库）只能治标，最终通过纯 Python 重写 + 缓存策略才彻底解决；
3. 最终我采用了"一次计算、多次复用"的 PE 缓存策略，大幅提升了后续实验的稳定性。

### 2.3 实验管理与自动化

8 组实验均按统一规范产出，包括标准化的 CSV 指标表和 Markdown 实验记录。这个流程让我习惯了**结构化实验管理**的重要性——当实验数量达到一定规模时，零散的文件组织会导致对比分析极其困难。

### 2.4 PE Graph 消融的"幽灵结果"——一次代码审查教训

在 seed=62 的 PE Graph 消融实验中，出现了一个极度反常的结果：**PE Graph=1（主实验）与 PE Graph=0（消融实验）的 7 项指标完全一致，精确到小数点后 7 位**。

两轮独立训练（尽管同 seed）产生完全相同的输出，在深度学习中几乎不可能——除非两次运行实际上使用了完全相同的模型配置。这个疑点促使我逐行审查自己之前添加的 PE 缓存代码：

```python
# 我自己写的缓存逻辑（train_pediffwavenet_noleak.py）
if os.path.exists(pe_cache_pe) and os.path.exists(pe_cache_mat):
    # 缓存路径: 直接从文件加载 PE_mat
    PE_mat = np.load(pe_cache_mat).astype(np.float32)
else:
    # 非缓存路径: 调用 build_graphs 计算
    S, T_mat, PE_mat = build_graphs(...)
    if not args.use_pe_graph:      # ← BUG: 这一行在 else 里面!
        PE_mat = np.zeros_like(...)
```

**问题根源**：`use_pe_graph=0` 时 `PE_mat` 的置零操作被放在了 `else` 分支内部。当 PE 缓存命中时（所有后续实验都走这条路径），置零代码**永远不会执行**。两组实验都加载了缓存的完整 PE 邻接矩阵，`use_pe_graph=0` 成了无效参数。

**影响范围**：4 组标记为 `g3_noPEgraph_*` 的消融实验实际运行的是完整 PE-DiffWaveNet（PE Graph=1），近 5 小时的 GPU 训练时间被浪费。这批实验被重命名为 `g3_pedw_*` 后归入主实验系列。

**教训**：
1. **代码修改需要审视所有执行路径**——尤其是 if/else 分支中的副作用。我在添加缓存逻辑时只关注了"加载提速"，忽略了原有控制流中藏在 `else` 里的业务逻辑。
2. **消融实验的异常结果要警惕**——"一切都相同"往往不是"该模块不重要"，而是"该模块根本没被关掉"。如果一个消融变量对结果零影响，首先怀疑自己的实验设计。
3. **别人的直觉值得倾听**——用户的一句"这两个实验应该不能直接比较"促使我重新审视代码，最终发现了 bug。科研中的"这个结果好像不太对"往往是错误的第一信号。

修复后，PE Graph=0 的置零逻辑被移到了 `if/else` 分支之外，确保无论是否使用缓存都会执行。这段代码现已合并入正式版本。

## 三、模型理解与洞察

### 3.1 扩散模块的真正价值

通过 4 组消融对比（diffusion vs noDiff），我发现了一个反直觉的规律：**扩散模块对整体 RMSE 的影响微乎其微（|Δ| < 0.3），但关闭后 Peak RMSE 恶化 1.4~1.8**。

这说明扩散过程的核心贡献不在于"降低平均预测误差"，而在于"细化极端值的概率分布"。对于臭氧预测的实际应用场景（高浓度 O3 的健康预警），这个发现尤为重要——**整体指标好看未必代表模型在关键场景下表现好**。

### 3.2 参数敏感度排序

pre_len ≫ seq_len ≫ diffusion 的排序说明：
- **预测步长是模型性能的第一决定因素**——从预 6 小时缩短到 3 小时，RMSE 下降 22%；
- 历史窗口的影响居中——更长≠显著更好，24h vs 12h 的差距在 5% 左右；
- 扩散模块的影响相对最小，但在峰值预测上有独特贡献。

### 3.3 收敛速度与泛化能力的权衡

无扩散模型普遍收敛更快（best epoch 减少 15~70%），但 Val RMSE 在 best epoch 后反弹更剧烈。这提示：**扩散过程相当于一种隐式的正则化机制，虽然减慢了训练，但提升了泛化能力**。

## 四、方法论收获

1. **消融实验的设计思路**：每次只改变一个变量，固定其他参数，是验证模型组件贡献的金标准。
2. **标准化输出格式的重要性**：统一的 4 文件格式（log/csv/md/sh）使得 8 组实验的对比汇总可以在几分钟内完成。
3. **缓存策略的价值**：对于不随参数变化的计算（如 PE 特征），一次计算多次复用可以极大提升实验效率并避免重复踩坑。
4. **记录比记忆可靠**：每轮实验的 experiment_log.md 不仅是文档，更是排除故障时的第一手线索。

## 五、总结

这次实验让我系统性地理解了 PE-DiffWaveNet 各组件的作用。最核心的认知是：**模型评估不能只看整体 RMSE/MAE——对于臭氧预测这样的任务，峰值预测精度、参数敏感度、收敛稳定性等都是同等重要的维度**。扩散模块看似"可有可无"（整体 RMSE 几乎不变），实则在最需要它的高浓度场景下发挥着不可替代的作用——这正是消融实验存在的意义。
